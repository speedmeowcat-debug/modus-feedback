# Обратная связь и предложения сотрудников

MVP для хакатона ГК «Модус Трейд». Сотрудник подаёт проблему, предложение или отзыв; система присваивает номер и назначает ответственного по правилам; ответственный уточняет, решает или мотивированно отклоняет; автор видит ход и итог; руководитель и администратор видят обзор и аналитику.

## Демо без установки

https://modus-trade-feedback.vercel.app

**Логин и пароль не нужны.** На странице входа, в блоке «Демонстрационный вход», нажмите на любой тестовый аккаунт, и вы сразу войдёте под этой ролью:

- «Сотрудник закупок» — подать обращение и следить за ним;
- «Руководитель закупок» — рассмотреть обращения своего подразделения;
- «IT-специалист» — ответственный со своей очередью;
- «Администратор системы» — все обращения, аналитика и настройки.

Ещё 19 ролей из датасета — под кнопкой «Остальные тестовые аккаунты». Чтобы сменить роль, нажмите «Выйти» внизу слева и выберите другой аккаунт.

## Запуск локально

Нужен Node.js 20+ (проверено на 24).

```bash
npm install
cp .env.example .env.local
npm run dev
```

Откройте http://localhost:3000. При первом запуске создаётся локальная база (PGlite, каталог `.data/pglite`), применяются миграции и загружаются 20 обращений датасета.

- `npm test` — интеграционные тесты серверного слоя (15 тестов: PGlite в памяти и путь через драйвер `pg`).
- `npm run build && npm start` — продакшен-сборка.
- `npm run db:reset` — удалить локальную базу (при остановленном сервере), при следующем запуске она создаётся заново.

## Демо-аккаунты

При `DEMO_MODE=true` на странице входа есть кнопки входа под тестовыми аккаунтами (без ввода пароля). Имена аккаунтов равны условным ролям датасета. Для основного сценария: «Сотрудник закупок», «Руководитель закупок», «IT-специалист», «Администратор системы». Пароль демо-аккаунтов задаётся переменной `DEMO_PASSWORD` в `.env.local`, логины перечислены в `src/db/seed.ts`.

## Сценарий демонстрации (60–90 секунд)

1. Сотрудник закупок: «Новое обращение», тип «Проблема», категория «Межотдельное взаимодействие». После отправки виден номер и ответственный.
2. Руководитель закупок: «Моя очередь», открыть обращение, «Запросить уточнение».
3. Сотрудник закупок: уведомление, блок «Нужен ваш ответ», ответ.
4. Руководитель закупок: «Зафиксировать: реализовано» с текстом итога. Затем «Обзор» и «Аналитика».
5. Администратор: «Настройки → Маршрутизация», проверка «кто получит обращение»; «Пользователи → Отсутствует» показывает резервное назначение.

## Что реализовано

- Вход, сессии в БД (в cookie случайный токен, в базе его хэш), пароли scrypt, 4 роли.
- Создание обращения: тип, категория, подразделение, заголовок, описание, предполагаемое решение, файл. Серверная валидация, защита от двойной отправки.
- Маршрутизация по редактируемым правилам (категория, уточнение по типу и подразделению), резервный ответственный, причина назначения в истории.
- Статусы: новое, на рассмотрении, в работе, ожидает уточнения, реализовано, отклонено, закрыто. Обязательный текст для уточнения, итога и отказа.
- Комментарии, внутренние заметки, вложения, полная история, уведомления внутри приложения.
- Списки с поиском и фильтрами (статус, тип, категория, подразделение, приоритет, срок), индикаторы просрочки и отсутствия первого ответа.
- Аналитика запросами к сохранённым данным: типы, статусы, категории, подразделения, доля завершённых, время до первого ответа, похожие обращения (пересечение слов, без ML).
- Администрирование: категории и сроки, правила, пользователи, параметры, журнал изменений.
- Адаптив: телефон, планшет, десктоп.

## Права доступа

Проверяются на сервере в сервисах (`src/lib/services`), интерфейс только скрывает недоступное. Любая выборка обращений проходит через `scopeSql`.

| Роль | Видит |
| --- | --- |
| Сотрудник | свои обращения |
| Ответственный | свои и назначенные ему |
| Руководитель | свои, назначенные и обращения своего подразделения; может менять ответственного |
| Администратор | всё, настройки |

Чужое обращение и несуществующий номер выглядят одинаково. Файлы отдаются только тем, кто видит обращение, и только на скачивание.

## Данные и допущения

- Тексты, номера, типы, категории, авторы, приоритеты, статусы, ответственные и «пример дальнейшего действия» взяты из «Датасет.docx» скриптом без ручного набора; тест сверяет базу с исходником.
- В датасете нет дат. Даты демо-набора синтетические, помечены в базе (`dates_synthetic`, `is_synthetic`) и в интерфейсе. В аналитике есть переключатель «Без демо-набора».
- Подразделения, принадлежность условных ролей к ним и роли доступа в датасете не заданы: это допущения, см. `src/db/seed.ts`.
- У обращений датасета нет заголовка: показывается «тип: категория».

## Архитектура

- Next.js 15 (App Router, серверные действия), TypeScript, Tailwind CSS 4, lucide-react, zod.
- PostgreSQL. Локально встроенный PGlite, при заданном `DATABASE_URL` драйвер `pg` (Supabase, Neon, свой сервер). Миграции в `src/db/migrations.ts`, сид в `src/db/seed.ts`.
- `src/lib/domain.ts` — словарь статусов и действий; `src/lib/services` — бизнес-логика и права; `src/app/actions.ts` — серверные действия; `src/components` — дизайн-система (токены в `src/app/globals.css`).

## Ограничения и что не готово

- Демо развёрнуто на Vercel (ссылка в начале README), инструкция по развёртыванию в `docs/DEPLOY.md`. Для Vercel нужен внешний PostgreSQL в `DATABASE_URL`.
- Интеграции с 1С и Битрикс24, клиентские опросы и NPS не реализованы (roadmap). Уведомления только внутри приложения.
- Нет смены пароля пользователем, SSO, e-mail. Ограничение перебора пароля хранится в памяти процесса.
- Вложения лежат в базе (до 5 МБ), антивирусной проверки нет.
- Нет тёмной темы. Автоматизированных UI-тестов нет: интерфейс проверялся вручную в браузере.
