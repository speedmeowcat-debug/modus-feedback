# Сценарий защиты, 3–4 минуты

Хронометраж рассчитан на спокойный темп. Текст в кавычках можно говорить близко к написанному.

## До выступления

1. Запустить приложение, открыть страницу входа. Для чистого состояния: остановить сервер, `npm run db:reset`, запустить снова.
2. Открыть два окна браузера (обычное и инкогнито), чтобы не тратить время на выход и вход: в первом сотрудник, во втором руководитель.
3. Заранее набрать текст обращения в заметке, чтобы вставить его, а не печатать.
4. Держать под рукой резервную запись экрана на случай проблем с сетью или проектором.

## 0:00–0:30. Проблема

«Сотрудник замечает проблему или придумывает улучшение. Сегодня он говорит об этом в чате или коллеге. Дальше возможны три исхода: обращение забыли, оно попало не тому человеку, или его рассмотрели, но автор так и не узнал результат. Компания при этом не видит, какие проблемы повторяются.»

«Мы сделали работающую систему, в которой у каждого обращения есть номер, ответственный, срок и итог.»

## 0:30–2:00. Демонстрация

| Время | Действие | Что сказать |
| --- | --- | --- |
| 0:30 | Вход как «Сотрудник закупок», «Новое обращение» | «Форма на одну минуту: тип, категория, описание. Файл по желанию.» |
| 0:45 | Тип «Проблема», категория «Межотдельное взаимодействие», вставить текст, отправить | «Обращение сразу получило номер и ответственного. Система назначила его по правилу категории и записала причину в историю.» |
| 1:00 | Второе окно: «Руководитель закупок», «Моя очередь», открыть обращение | «Ответственный видит свою очередь, сверху то, что горит по сроку.» |
| 1:10 | «Запросить уточнение», вопрос, отправить | «Не хватает деталей: задаём вопрос автору.» |
| 1:20 | Первое окно: уведомление, блок «Нужен ваш ответ», ответить | «Автор видит вопрос прямо в обращении. После ответа оно само возвращается в рассмотрение.» |
| 1:35 | Второе окно: «Зафиксировать: реализовано», текст итога | «Закрыть без итога нельзя. Отказ без причины тоже.» |
| 1:45 | Первое окно: карточка с итогом | «Автор видит, что сделано.» |
| 1:50 | Второе окно: «Аналитика» | «Руководитель видит долю завершённых, время первого ответа, просрочки и похожие обращения. Всё считается по базе в момент открытия.» |

Если остаётся время: войти администратором, «Настройки → Пользователи», отметить руководителя закупок отсутствующим, на вкладке «Маршрутизация» нажать «Проверить» — обращение уйдёт резервному ответственному.

## 2:00–2:40. Как устроено

«Одно приложение на Next.js и PostgreSQL. Права проверяются на сервере: сотрудник не откроет чужое обращение даже по прямой ссылке, и по номеру нельзя понять, существует ли оно. Маршрутизация и поиск похожих обращений работают по понятным правилам, без нейросетей: администратор всегда может объяснить, почему обращение попало к конкретному человеку.»

«Все 20 обращений из датасета загружены без изменений, тест сверяет базу с исходным документом. Дат в датасете нет, поэтому даты демо-набора синтетические и так помечены. Новое обращение проходит тот же путь, что и демонстрационные.»

## 2:40–3:20. Ценность и проверка

«Что это даёт компании: обращения не теряются, у каждого есть ответственный и срок, решения сохраняются, повторяющиеся темы видны.»

«Четыре показателя из ТЗ считаются уже сейчас: доля рассмотренных, время до первого ответа, доля с зафиксированным итогом, число реализованных улучшений. Целевые значения мы не придумывали: их нужно определить вместе с компанией на пилоте.»

Не называть экономический эффект в деньгах и часах: данных для такой оценки нет.

## 3:20–4:00. Что дальше

«Следующий шаг — пилот в одном-двух подразделениях. Для него нужны вход через Битрикс24 и уведомления там же: это убирает отдельные пароли и приводит ответственного в обращение без захода в систему. Затем конфиденциальные обращения, объединение дублей и задачи в Битрикс24 по принятым предложениям. Опросы и клиентская обратная связь идут третьим этапом, как и предлагает ТЗ.»

«Интеграции в MVP не реализованы: уведомления пока только внутри приложения. Архитектура это учитывает, точки подключения описаны.»

## Ответы на вероятные вопросы

| Вопрос | Ответ |
| --- | --- |
| Почему без анонимности? | По ТЗ она необязательна. Без автора нельзя задать уточняющий вопрос и показать итог. Для чувствительных тем в плане есть конфиденциальные обращения: автора видит только доверенный сотрудник |
| Что если ответственный в отпуске? | Администратор отмечает отсутствие, новые обращения уходят резервному ответственному с записью причины. Заместители по каждому сотруднику запланированы на пилот |
| Как находятся повторы? | По совпадению значимых слов: минимум три общих слова и заметная доля от короткого текста. Плюс категории, где проблем две и больше. На большом объёме заменяется полнотекстовым поиском PostgreSQL |
| Почему свои, а не задачи Битрикс24? | У обращения другой жизненный цикл: маршрут по категории, уточнения, обязательный итог для автора, аналитика по темам. Задачи Битрикс24 подходят для реализации принятого предложения, эту связку мы предлагаем на втором этапе |
| Что с безопасностью? | Пароли в виде хэшей, сессии в базе, проверка прав на сервере, параметризованные запросы, проверка типа и размера файлов, журнал изменений настроек. До промышленной эксплуатации нужны SSO, резервное копирование и антивирусная проверка вложений |
| Насколько это готово? | Основной сценарий работает на произвольных данных, покрыт 15 интеграционными тестами. Не готовы интеграции, внешние уведомления и размещение в инфраструктуре компании |
| Что реализовано, а что имитация? | Имитаций нет. Синтетические только даты демо-набора. Интеграции не имитируются, а описаны как план |
