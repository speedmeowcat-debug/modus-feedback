# Размещение

Деплой из этой среды не выполнялся: для него нужны учётные записи владельца проекта. Ниже два проверенных по шагам варианта и то, что именно проверено.

## Что проверено

| Проверка | Результат |
| --- | --- |
| `npm run build` | Собирается |
| `npm start` с PGlite | Запускается, применяет миграции, загружает датасет, отдаёт страницы и заголовки безопасности |
| Код через драйвер `pg` по протоколу PostgreSQL | Проходит тест `tests/pg-driver.test.ts` (сервером служит PGlite на локальном сокете) |
| Настоящий сервер PostgreSQL (Supabase, Neon) | Не проверялось |
| Vercel | Не проверялось |

## Вариант А. Vercel и внешний PostgreSQL

Подходит для публичной ссылки на время хакатона. На Vercel нет постоянного диска, поэтому встроенная база не годится: нужен внешний PostgreSQL.

1. Создать базу PostgreSQL в Supabase или Neon и скопировать строку подключения. Для Supabase брать строку пулера (Session pooler), для Neon обычную с `sslmode=require`.
2. Загрузить репозиторий на GitHub и импортировать проект в Vercel.
3. В настройках проекта задать переменные окружения:

   | Переменная | Значение |
   | --- | --- |
   | `DATABASE_URL` | строка подключения |
   | `DEMO_MODE` | `true` на время демонстрации |
   | `DEMO_PASSWORD` | свой пароль для демо-аккаунтов |

4. Запустить деплой. При первом обращении к сайту приложение само применит миграции и загрузит датасет.
5. Открыть сайт, войти под демо-аккаунтом, пройти сценарий из `PITCH.md`.

Замечания:

- Первый запрос после деплоя дольше обычного: создаётся схема и 23 пользователя.
- Если первый запрос придёт одновременно в два экземпляра, сид может выполниться дважды и второй завершится ошибкой уникальности. Достаточно открыть сайт один раз самому до показа.
- Ограничение размера тела запроса на Vercel около 4,5 МБ: файлы крупнее не загрузятся, хотя лимит приложения 5 МБ.
- Счётчик попыток входа хранится в памяти экземпляра и на serverless работает неточно.

## Вариант Б. Один сервер с диском

Подходит для запуска внутри компании или на VPS. Внешняя база не нужна.

```bash
npm ci
npm run build
npm start
```

Данные лежат в каталоге `PGLITE_DIR` (по умолчанию `.data/pglite`). Каталог нужно сохранять между перезапусками и включить в резервное копирование. Запускать можно только один экземпляр приложения: PGlite не поддерживает два процесса на одном каталоге.

Если сайт открывается по HTTP без TLS и не с `localhost`, браузер не сохранит cookie сессии с признаком `Secure`. Для такого стенда задайте `INSECURE_COOKIES=true`. Для реальной работы нужен HTTPS.

Для роста нагрузки задайте `DATABASE_URL` на обычный PostgreSQL: код тот же.

## Перед показом

1. Сбросить данные к чистому датасету. Вариант Б: остановить сервер и выполнить `npm run db:reset`. Вариант А: пересоздать схему `public` в базе.
2. Проверить вход под четырьмя основными демо-аккаунтами.
3. Пройти сценарий один раз целиком и снова сбросить данные.
4. Записать резервное видео прохождения сценария.

## После хакатона

- `DEMO_MODE=false`, сменить пароли, удалить демо-аккаунты.
- Подключить резервное копирование базы.
- Закрыть доступ извне или подключить корпоративный вход.
